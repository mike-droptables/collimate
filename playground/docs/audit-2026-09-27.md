# Browser demo audit notes — 2026-09-27

These notes are the browser demo's part of the 2026-09-27 audit of both repositories (the main report is docs/reference/audit-report-2026-09-27.md), kept in this folder because AGENTS.md rule 6 keeps every mention of the demo out of the main code and docs.

## The browser demo (its own folder)

This section covers the playground (browser demo) and the CI, build and API code it depends on or overlays. All paths are in the app repo. Findings that touch shared code (api/, frontend/, .github/) appear here because the playground build, its CI jobs or its shim are affected by them.

### Make CI check out an SDK that exists

Covers: F1097 (files: .github/workflows/test.yml, .github/workflows/playground.yml). Severity: high.

**What is there now.** Every SDK-dependent job checks out `mike-droptables/collimate-sdk`, which is an empty repository (the GitHub API returns 409 "Git Repository is empty"). On the private repo, playground.yml's `build` and `demo-unit` jobs fail at that checkout step on every push (run 36350514827), while test.yml gates `api-tests`, `api-typecheck` and `desktop-e2e` off with `if: !github.event.repository.private`. The public app mirror holds only the Pages site and has no workflows, because sync-public is disabled (`SYNC_ENABLED=false`).

**Why it matters.** The backend pytest suite, pyright and the Electron e2e run in no CI at all, and the playground workflow is red on every push, so a real playground regression cannot be told apart from the standing failure. The gate comments ("the public mirror is the only env with the SDK source") are stale.

**Options.**
1. Check out the private `mike-droptables/collimate-sdkdev` with a read-only fine-grained token or deploy key in all five jobs, and remove the private-repo gates and their comments (test.yml:85-88, :130-132, :224-226). Pros: every suite runs where development happens, against the matching SDK HEAD. Cons: a long-lived cross-repo secret and private CI minutes. Effort: hours.
2. Gate playground.yml `build`/`demo-unit` the same way test.yml does. Pros: no secret, red runs stop. Cons: with the mirror empty and sync paused, these jobs and the backend suite run nowhere. Effort: under an hour.
3. Populate and resume the public SDK mirror, and keep pointing CI at it. Pros: no secret. Cons: the SDK lags private HEAD by up to a day, so any change that spans both repos fails CI until the next sync. Effort: hours, plus the decision to resume publishing.

**Recommendation.** Option 1, because it is the only option under which the backend, typecheck, e2e and demo suites all run against the SDK they are developed with.

Cons: rule 6 and the playground README must be rewritten, and notes can start to describe demo handling, which is the drift the rule exists to stop. Effort: under an hour.

### Move CI and the documented floor off Node 20

Covers: F1062, F1095 (files: .github/workflows/test.yml, .github/workflows/playground.yml, .github/workflows/publish-pypi.yml, .github/workflows/release-desktop.yml, README.md). Severity: medium.

**What is there now.** Every workflow pins `node-version: "20"` (test.yml:40,59,148,170,206,240; playground.yml:52,113; publish-pypi.yml:50; release-desktop.yml:195), and README.md:65 says "Node >= 20". Node 20 reached end of life on 2026-04-30. Electron, @electron/get, @electron/rebuild and node-abi in desktop/package-lock.json declare engines `>=22.12.0`, so the desktop jobs already install below their dependencies' floor (npm only warns), and the SDK's Claude installer needs Node 22 at runtime.

**Why it matters.** CI and users run on an unsupported runtime, and the README floor is already wrong for desktop. Nothing fails today, but the first dependency that turns the engine warning into an error breaks release builds.

**Options.**
1. Node 22 LTS everywhere, README to "Node >= 22.12", optionally `engines.node` in desktop/package.json. Pros: matches the dev machine (v22.22.1), the Electron floor and the SDK installer. Cons: maintenance LTS, ends April 2027. Effort: an hour plus one full CI pass.
2. Node 24 LTS everywhere. Pros: longest support. Cons: differs from the dev machine, and vitest, electron-builder and Playwright need a full compatibility pass. Effort: hours to a day.

**Recommendation.** Option 1, because it matches what the dependencies and the dev machine already require, and the move to 24 can ride with the frontend toolchain bump below.

### Frontend toolchain: how far and how fast to update

Covers: F1094, F1854 (files: frontend/package.json, frontend/package-lock.json, frontend/vitest.config.ts, frontend/vite.config.ts, .github/workflows/test.yml). Severity: medium.

**What is there now.** frontend/ locks vite 6.4.3, vitest 3.2.7, @vitejs/plugin-react 4.7.0, TypeScript 5.9.3, jsdom 25.0.1 and @playwright/test 1.59.1, while desktop/ uses TypeScript ^7 and resolves vite 7.3.6, and playground/package.json pins @playwright/test 1.63.0. In-range updates are pending (Tailwind 4.2.1 to 4.3.3, Playwright to 1.63.0, plus tailwind-merge, typescript-eslint and eslint-plugin-react-refresh minors). Commit ef650baf held Playwright and Tailwind back on purpose. The playground build reuses `frontend/node_modules` (playground/build.sh), so a frontend Tailwind bump changes the CSS the playground visual suite renders; the frontend Playwright version does not affect those baselines, which run in the pinned v1.63.0 image, and no baseline PNGs are committed right now.

**Why it matters.** Vite 6 is out of active support, the remaining npm advisories need vitest 5 (per ef650baf), the repo carries two vite majors and two Chromium downloads, and each deferred step makes the eventual migration larger.

**Options.**
1. Staged: now, the three tooling minors plus frontend Playwright 1.63.0 (floor `^1.63.0`), keeping Tailwind held; then vite 7 with plugin-react 5 on vitest 3; then vitest 4/5 with vite 8; TypeScript and jsdom as separate PRs. Tailwind 4.3 goes in together with a playground visual re-baseline. Pros: each step is small and bisectable, and Playwright is one version across frontend, playground and the api live suite. Cons: several PRs, and the vite 7 / vitest 3 stop is short-lived. Effort: hours now, then about a day per stage.
2. One PR for the whole toolchain (vite 8, plugin-react 6, the vitest 5 family, TypeScript 6 or 7, current @types/node) together with the Node move. Pros: one migration to current majors. Cons: Rolldown output, the vitest browser-provider API (vitest.config.ts) and coverage changes land at once and are hard to bisect. Effort: days.
3. Only the three tooling minors (lockfile only), everything else stays. Pros: respects the hold-back completely, no visual or browser churn. Cons: vite 6 stays unsupported, the advisories stay, and the split with desktop/ persists. Effort: under an hour.

**Recommendation.** Option 1, because the Playwright alignment and the minors are cheap and safe today, and staging keeps the vite and vitest breakages separable.

### Service-worker restart loses page readiness

Covers: F1065 (files: playground/web/sw.js, playground/web/boot.js, playground/README.md). Severity: low.

**What is there now.** `hosts` (sw.js:33) is in-memory service-worker state, and boot.js sends `page-ready` only at boot and on `controllerchange` (boot.js:102-112), which a worker restart does not fire. After a restart, a renderer iframe request can get 503 "No page is hosting the demo runtime" until the page's next own /api request (for example the SSE reconnect) re-registers it, and the 60 s headers timeout for that page starts only after the 5-minute `MAX_BOOT_WAIT_MS`. Whether browsers terminate the worker while an SSE response is open has not been measured.

**Why it matters.** The visible effect is a transient renderer load error and a hung request that surfaces after 6 minutes instead of 1.

**Options.**
1. On a newly seen top-level client the worker posts `ready?` and boot.js answers with `announceReady()`; optionally, when the pool is empty, ping every top-level window and wait up to about 1 s before returning 503. Pros: event-driven, two files, no polling. Cons: a new message type in the bridge protocol. Effort: hours.
2. boot.js re-sends `page-ready` on `visibilitychange`/`focus` or on an interval. Pros: one-file change. Cons: heuristic; a hidden tab stays unannounced until the next event. Effort: an hour.
3. Leave it and document restart behavior in the README "Request path" section. Pros: no code. Cons: the transient 503 can still show as a renderer error. Effort: under an hour.

**Recommendation.** Option 1, but only after a quick Chrome and Firefox check shows the worker does get terminated with an SSE stream open; if it does not, take option 3.

### Pin the floating CI and demo tools

Covers: F1123, F1071 (files: .github/workflows/test.yml, playground/serve.sh, playground/package.json, playground/package-lock.json, api/pyproject.toml). Severity: low.

**What is there now.** test.yml:28 runs `pip install ruff` and test.yml:158 runs `npx -y pyright`, both unpinned. playground/serve.sh:27 runs `npx --yes serve@latest` as the Playwright webServer (playwright.config.ts:58), and its own comment says serve's `cleanUrls`/`rewrites` semantics are load-bearing for sandbox.html's query string. The script also leaks its mktemp config because `exec` replaces the shell. Everything else, including @playwright/test and the visual-job container, is pinned exactly.

**Why it matters.** An upstream release can turn CI red or change lint findings with no change in the repo, and a serve major could break the demo e2e silently.

**Options.**
1. Mixed: `pip install ruff==<ver>` inline (api-lint is venv-free by design and cannot `uv sync` without the SDK), pyright in api's dev group run with `uv run pyright`, and `serve` as an exact devDependency in playground/package.json with serve.sh calling `npx --no-install serve` and writing its config under the gitignored `.stage/`. Pros: reproducible, the lockfiles own two of the three versions. Cons: adds a dependency and lockfile entries; a bare `bash serve.sh` without `npm ci` fails. Effort: an hour.
2. Pin all three inline (`ruff==x`, `pyright@x`, `serve@x`). Pros: trivial, job shapes unchanged. Cons: versions scattered outside the lockfiles and easy to forget; serve still downloads at runtime without an integrity hash. Effort: under an hour.
3. Keep floating. Pros: always the newest checks. Cons: failures unrelated to any change, and a run's behavior depends on the day. Effort: none.

**Recommendation.** Option 1, because it follows the pinning discipline the rest of the repo already uses while respecting api-lint's venv-free design.

### Renderer precompile in the server build uses a floating esbuild

Covers: F1086 (files: build/build_server.sh, docs/ai_tools/notes/project_revendor_commands.md). Severity: low.

**What is there now.** Step 1.4 of build/build_server.sh runs `npx --yes --quiet esbuild` once per `main.tsx` (23 renderers) before the frontend `npm install`, so npx resolves whatever esbuild it finds (0.28.2 locally, about 12 s per build) instead of the frontend's locked 0.25.12, and a compile error only warns. playground/build/vendor.py runs the same transform with `frontend/node_modules/.bin/esbuild` and raises on failure, so the demo and the server build can emit different `main.js`.

**Why it matters.** The two builds of the same renderers can differ, and the re-vendor note calls this step mandatory while the script treats it as optional.

**Options.**
1. Move the frontend `npm install` ahead of step 1.4 and run the pinned binary once over all entry points, failing on error. Pros: about 12 s faster, reproducible, matches the demo. Cons: one broken renderer blocks every build, including dev_server runs where the babel fallback would have covered it. Effort: hours.
2. Same reorder and pinned binary, but keep the per-file loop and warn-only. Pros: one esbuild version everywhere, still tolerant of a broken renderer. Cons: keeps 23 spawns (cheap without npx). Effort: an hour or two.
3. Leave it. Pros: no reordering. Cons: version drift from the frontend and the demo, 12 s per build. Effort: none.

**Recommendation.** Option 2, because version agreement with the demo is the real gain and the warn-only posture is a deliberate fallback that should change only by separate choice.

### Scope playground.yml permissions to the deploy job

Covers: F1099 (files: .github/workflows/playground.yml). Severity: low.

**What is there now.** playground.yml:27-30 grants `pages: write` and `id-token: write` to every job, including build, demo-unit, e2e and visual, which run `npm ci` and `uv sync` install scripts. Concurrency is `pages-<ref>` with `cancel-in-progress: false`, so a superseded PR run keeps running for up to about 45 minutes (GitHub keeps only one pending run per group, so it does not queue indefinitely).

**Why it matters.** Same-repo PR code can mint OIDC tokens it never needs, and PR feedback is slower than it has to be.

**Options.**
1. Top-level `contents: read`, the Pages permissions on `deploy` only, and `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`. Pros: least privilege and faster PR feedback; main deploys are never cancelled. Cons: two behavior changes in one edit. Effort: under an hour.
2. Scope permissions only. Pros: pure hardening, timing unchanged. Cons: stale PR runs keep running. Effort: under an hour.
3. Keep GitHub's starter-template layout. Pros: familiar. Cons: install scripts keep a broader token. Effort: none.

**Recommendation.** Option 1, because both changes are standard and main deploys stay protected.

### Should the isolation guard also scan the SDK

Covers: F1110 (files: playground/tests/check_isolation.sh, playground/README.md). Severity: low.

**What is there now.** check_isolation.sh:55 scans only this repo's `git ls-files`; the `collimate-sdk` symlink is gitignored, and the SDK's ci.yml has no equivalent check, although AGENTS.md rule 6 and playground/README.md:15 cover the SDK. A scan of the SDK today finds only legitimate hits: `wasMeasurable` in renderers/live/terminal/main.tsx and "wasm/worker" in renderers/visual/pdf/main.tsx:11, so any scan needs allowlist entries (a word boundary does not exclude `wasMeasurable`).

**Why it matters.** The rule written for the SDK is enforced by no tool; there is no current leak and no known pressure, since the demo patches only api/ and frontend/.

**Options.**
1. Scan the SDK checkout when present (found the way playground/build.sh:28-34 does), prefix hits with `sdk:`, allowlist the two lines, and print a note when absent. Pros: one token list; playground.yml's build job already has the SDK. Cons: the app script depends on the SDK layout, it covers nothing in `api-lint`, and SDK-only pushes are checked only on the next app run. Effort: an hour or two.
2. A copy of the guard in the SDK's ci.yml. Pros: checks every SDK push. Cons: two token lists that drift, and the SDK gains knowledge that a demo exists, which rule 6 is meant to avoid. Effort: an hour.
3. Leave it to review. Pros: no cost. Cons: the SDK half of the rule stays unenforced. Effort: none.

**Recommendation.** Option 1, because it enforces the rule where the SDK is already checked out without teaching the SDK about the demo.
